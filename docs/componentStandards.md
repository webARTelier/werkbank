# Component authoring standards

Distilled from the reworked components (`accordion`, `adaptiveScrollFade`,
`countdown`, `dateInputFormat`, `dialog`, `flexNeighborMarker`,
`formValidation`). This is the checklist to follow when building or reworking a
component, so it does not have to be re-derived each time. Read it together with
the top-level `CLAUDE.md` (naming, DI-vs-import, focus-ring conventions) and
[`preEnhancement.md`](preEnhancement.md) (the ready attribute and the state
that covers the gap between the first paint and `init()`).

> **Comment line length.** Keep the *text* of code comments within **78
> characters** per line so they never wrap awkwardly in a narrow editor pane.
> This applies to JS block/line comments, SCSS comments and the HTML comment
> banners. Code itself is not hard-wrapped.


## 1. Files per component

Every component folder (`src/components/<name>/`) ships exactly these files,
each named after the folder (`<name>.js` etc.):

| File            | Purpose                                                       |
| --------------- | ------------------------------------------------------------ |
| `<name>.js`     | Behaviour. Exports `init(el, services)`; never self-runs.    |
| `<name>.scss`   | Styles (compiled to `dist/css/<name>.min.css`). A one-line   |
|                 | stub (`// <name> styles`) for behaviour-only components.     |
| `<name>.html`   | Copy-paste snippet with a comment banner explaining wiring.  |
| `demo.html`     | Standalone live demo loading the built `/dist` assets.       |
| `readme.md`     | Human documentation (see §8).                                |

`_shared/js/registry.js` is **auto-generated by Gulp** from the module file
names — never hand-edit it. The module id in `data-js-behavior="<name>"`
equals the registry key (the camelCase module name).


## 2. The boot loader (`_shared/js/boot.js`)

`boot.js` is the tiny runtime that ties every component together. It is the
**only** always-eager script: the build bundles it into `dist/js/boot.min.js`,
the snippet loads it on every page (see §7), and the author **never** imports a
component's `<name>.js` directly. Everything else is lazy.

**Composition root.** On load, `boot.js` builds the shared `services` object
**once** and keeps it at module scope so the same instances are reused for every
`init` call (including later re-scans). Today that is just the `reporter`
(`createReporter({ level: 'warn' })`); further shared collaborators are added
here. This is the DI seam described in `CLAUDE.md` — only configured/stateful
singletons belong in `services`; pure utilities are direct-imported into each
component's own lazy chunk instead.

**Two registries** (both from the auto-generated `registry.js`, see §1):

- `registry` — **page modules**, loaded lazily *per element*. Keyed by camelCase
  module name; each value is a `() => import('./modules/<name>.min.js')` thunk,
  so a module's code is only fetched when markup actually asks for it.
- `globalRegistry` — **global modules**, initialised **once per page**
  regardless of markup (populated from `config.registry.globalModules`; empty by
  default). These get `init(services)` — **no element** argument.

**Boot sequence.** `boot()` runs once on load: it first awaits
`initGlobalModules()`, then `initModulesInScope(document)`.

**Per-element init** (`initModulesInScope(scope = document)`):

1. Query `scope` for `[data-js-behavior]` elements. The elements are processed
   **concurrently** (`Promise.all`) — every module is its own lazily imported
   chunk, so awaiting one element before starting the next would lay n
   independent fetches end to end and enhance the last component n round trips
   after the first paint. The modules **on one element** still run in source
   order: `data-js-behavior="a,b"` may mean that `b` expects the markup `a`
   produced.
2. For each element, parse the attribute as a **comma-separated** list of module
   names (`'accordion,slider'` → `['accordion', 'slider']`), trimmed, empties
   dropped.
3. Look the name up in `registry`; a miss is reported via the reporter
   (prefix `"loader"`) and skipped.
4. **Double-init guard:** set `el.dataset['jsInit_<name>'] = '1'` *before*
   loading; an element already flagged for that module is skipped. This is why
   components must **not** add their own double-init guard (see §3).
5. `await load()` to fetch the chunk, verify `mod.init` is a function (else
   report), then `await Promise.resolve(mod.init(el, services))`. Any throw from
   loading or `init` is caught and reported — one broken module never aborts the
   rest of the page.

**Dynamically inserted markup.** `initModulesInScope` is exported for code
that injects markup after load (AJAX, template render, …); it calls
`initModulesInScope(newContainer)` to wire just that subtree, and the
double-init flags make it safe to call over a scope that already contains
initialised elements.

**Teardown.** `destroyModulesInScope(scope = document)` is the counterpart for
hosts that mount/unmount the same subtree repeatedly instead of doing a full
page (re)load (a JS framework re-rendering, an SPA route change). It calls
every cleanup function a module's `init()` returned (see §3) for elements
still in `scope`, then clears their double-init flags so a later
`initModulesInScope()` call over the same elements can `init()` them again.
Components that return nothing from `init()` are simply skipped — this is an
opt-in mechanism, not a requirement.


## 3. The `init` contract (JS entry point)

Boot (`_shared/js/boot.js`) lazily imports the module when it sees
`data-js-behavior="<name>"` and calls `mod.init(el, services)`. So:

- Export a single `export function init(el, services = {})`. Do **not**
  self-initialize on import.
- Pull collaborators off `services` (`const reporter = services.reporter;`).
- **Guard the element type first** and bail via the reporter on mismatch:

  ```js
  export function init(el, services = {}) {
    const reporter = services.reporter;

    if (!(el instanceof HTMLElement)) {
      reporter?.report(
        '<name>',
        'module was initialized on a non-element node.', el
      );
      return;
    }
    // ... construct / run
  }
  ```

- **Do not add a double-init guard** — the loader sets a per-element,
  per-module flag before calling `init`. Note it with the standard comment:
  `// Double-init is prevented by the loader (boot.js sets a per-element, //
  per-module flag before calling init), so no extra guard is needed here.`
- `services.reporter` is **optional** — always call it as `reporter?.report(...)`
  so the module degrades silently without it. The first argument is the
  component name used as the console prefix; use the **camelCase module name**
  (e.g. `'inlineSVG'`), not a lowercased form (the lowercase prefixes in
  `CLAUDE.md`'s "still open" list are legacy, not the target).
- **Own a ready attribute if the component has a pre-enhancement state.**
  `data-<name>-ready` (lowercase), held in `defaults` as `readyAttr`, set on
  the component root by `init()` and removed again by the cleanup function.
  It is only ever *written*, never read back. The stylesheet keys its
  pre-enhancement block off its absence, so the moment it is set matters: set
  it when the component can actually operate the state it declares — and, if
  `init()` can bail on unusable markup, set it on those paths too, so a bail
  never leaves content hidden behind a widget that does not exist. Never
  reuse the loader's `data-js-init_<name>`: that one is written *before* the
  chunk is imported. See [`preEnhancement.md`](preEnhancement.md) §3.
- **Optionally return a cleanup function** — `init` may `return () => { ... }`.
  The loader stores it and calls it from `destroyModulesInScope()` (§2). This
  matters only for state that outlives the component's own subtree: listeners
  on `window`/`document`, `matchMedia` change listeners, running
  timers/animations, or DOM nodes injected outside the element itself (e.g. a
  sentinel appended to `document.body`). Return nothing if the component holds
  no such state — a `ResizeObserver`/`MutationObserver` that only ever
  observes descendants of `el`, or listeners bound directly to `el`'s own
  nodes, die naturally when the host removes `el` from the DOM and need no
  explicit cleanup.


## 4. JS style & structure

- **2-space indent, single quotes, semicolons.** Prefer single quotes; switch
  to double quotes only to avoid escaping (e.g. a string containing an
  apostrophe). Every statement ends with a semicolon. Constants use camelCase
  like any other binding (no `UPPER_SNAKE_CASE`); avoid `else` — return early
  with guard clauses instead (see the code-style-guide skill).
- **One blank line before a leading comment inside a block.** When a block
  opens with a comment, a blank line separates it from the opening line —
  in every block (function/method/class body, `if` branch, loop, `switch` case,
  `try`/`catch`, callback, object literal) and without exception, including a
  block whose only content is that comment. Same rule as in SCSS — see the
  code-style-guide skill (JavaScript › *Comments*).
- Top of file: a **block header comment** (`/** … */`) that states, in prose:
  1. what the component does and *why it is needed* (the gap it closes);
  2. **what the platform already does** so the script does not reimplement it;
  3. **what the script adds** (numbered list);
  4. **accessibility** notes;
  5. **configuration** (every `data-*` option, all optional where possible).
- A `const defaults = { … }` object holds selectors, attribute names, class
  hooks and tunables — with a comment per entry. Behavioural hooks are **data
  attributes** (`data-fv-item`), not style classes, so the JS stays decoupled
  from the CSS.
- **Stateful controllers use a `class`** (`Dialog`, `FormValidation`,
  `FlexNeighborMarker`) constructed in `init`. **Stateless DOM transforms use
  plain functions** (`scaleSVG`, `inlineSVG`) — no instance/lifecycle needed.
- Use **class fields for bound handlers** (`handleClick = (e) => {…}`) so `this`
  is stable and listeners are removable.
- **Progressive enhancement is the core principle.** Lean on the native
  platform as the source of truth (`<dialog>`, `<details>`, Constraint
  Validation, `viewBox`) and only fill the gaps. Without JS the markup must stay
  usable.
- **Never write inline styles for state.** Toggle a **state class or data
  attribute** and let the SCSS react (accordion / adaptiveScrollFade /
  flexNeighborMarker pattern). Writes must be **idempotent**
  (`classList.toggle(cls, force)`) so a mutation that changes an element's box
  cannot feed back into a `ResizeObserver` as an infinite loop.
- **Pure utilities are direct imports** from `_shared/js/` as flat siblings
  (`import { rafThrottle } from './rafThrottle.js';`) — the build resolves them
  from there. A utility only one component imports is inlined into that
  component's lazy chunk; one that two or more import becomes its own chunk in
  `dist/js/modules/`, loaded alongside the first of them and then cached for
  the rest. So **the second consumer of a helper is the reason to hoist it**:
  duplicating it would ship it twice. **Configured/stateful collaborators come
  via `services`** (DI). See `CLAUDE.md`.
- Collapse bursts of resize/observer/scroll events into **one measurement per
  frame** with `rafThrottle`. Recompute on the real triggers: `resize`,
  `ResizeObserver`, `MutationObserver`, `document.fonts.ready`, `load`. Tear
  observers down when they are no longer needed (e.g. on dialog close).
- Read geometry, *then* write — do not interleave layout reads and writes.


## 5. Accessibility (non-negotiable)

- Reflect state into ARIA from the JS (`aria-expanded`, `aria-controls`,
  `aria-haspopup`, `aria-invalid`, `aria-describedby`, `role`) following the
  ARIA APG pattern for the widget.
- Give any programmatically focusable region an **accessible name** and a role;
  warn via the reporter if one cannot be derived rather than emitting an
  unlabelled region.
- Never let anything meaningful to AT depend on a **purely presentational**
  marker (e.g. `flexNeighborMarker`'s `has-neighbor` adds no ARIA at all).
- Purely decorative generated SVG/glyphs get `aria-hidden="true"` +
  `focusable="false"`.


## 6. SCSS conventions

- Header comment banner (`// ===` box) describing the component and, crucially,
  the **contract with the JS**: which class/attribute the JS toggles and that
  the script sets no inline styles.
- Declare the `--<name>-*` custom properties **on the component root**
  (`.m-<name> { … }`), not in `:root`, so the override surface stays scoped to
  the component and a single instance can be retuned in place (an inline
  `style="--<name>-x: …"` on that element still wins). They **map to the shared
  tokens** (`--space-*`, `--color-*`, `--an-duration`, `--an-ease`,
  `--borderRadius`, `--outlineOffset`; see `_shared/scss/_foundations.scss`,
  `_colors_semantic.scss`). Only a component that owns no root element to scope
  them to keeps them in `:root` — see the comments in `formValidation.scss` and
  `marquee.scss`.
- **All of them in ONE block at the top of the partial**, right after the
  `@use` lines — that block *is* the documented override surface, so a
  maintainer reads every knob in one place instead of hunting the file.
  Group them by kind with a short comment per group (Animation / Sizing /
  Spacing / Type scale / Colors) and name what a value is for where the name
  cannot say it (`--accordion-gap: var(--space-2xs); // gap between items`).
  Consequently **no rule further down references a shared token directly** —
  it goes through a `--<name>-*` property declared up there (`dateInputFormat`
  and `offCanvasNav` are the reference files). Two things legitimately sit
  outside that block: **per-variant overrides** of an already-declared
  property (`.m-backToTop--iconOnly { --backToTop-padding: … }`) and
  **state values the JS writes or a state rule flips** — those belong next
  to the rule that explains them (`--scrollFade-top`,
  `--offCanvasNav-panel-offset`, `--popover-fallback-*`).
- **BEM with an `m-` prefix** for styling classes (`.m-dialog__panel`); the JS
  must **not** hook onto `m-*` classes — it targets the element via
  `data-js-behavior` and behavioural `data-*` attributes. State classes the JS
  writes (`is-invalid`, `has-neighbor`, `is-scrollLocked`) are the styling hook.
- **Elements and modifiers are written inside the block, as `&__x` / `&--y`:**

  ```scss
  .m-dialog {
    --dialog-radius: var(--borderRadius);   // the token block, first
    …



    &__panel { … }



    &--wide &__panel { … }



    & [hidden] { … }
  }
  ```

  **Every selector block on this first level opens on three blank lines** — the
  same wide gap that separates top-level rules, because each is a part of the
  component in its own right and the gaps are what make the outline scannable.
  A leading comment belongs to its block, so the gap goes above the comment.
  Everything **deeper** stays at one blank line (concern groups, `&:hover` /
  `&::before`, state and media-query blocks inside a part), and three things on
  the first level do too: a block that is the **first** thing in its parent, the
  `& { … }` wrapper holding the component's own declarations after an
  `@include`, and at-rule blocks (`@media`, the viewport mixins,
  `@starting-style`).

  This is concatenation, not descendant nesting: `&__panel` compiles to
  `.m-dialog__panel`, so the emitted selector and its specificity are exactly
  those of the flat form — which is the point of BEM. It keeps everything the
  block owns in one place and reads as the component's outline. What stays
  **outside** is what cannot be expressed relative to the block: rules on
  script-injected nodes (`[data-lightbox-ui='viewer']`,
  `[data-dropdownnav-toggle]`) and any selector list mixing the two
  (`dropdownNav`'s link/label/toggle rule) — nesting a foreign selector under
  the block would silently turn it into a descendant. Where such a rule sits
  between block rules, the block is written in more than one `.m-block { }`
  section rather than moving rules across it: source order is cascade order.
- **A nested module gets a container from the outer one**, named
  `m-<outer>__<inner>` and shipped by the outer module's markup. That element
  carries the placement, and the inner module is retuned by setting its
  `--<inner>-*` knobs on its root from inside it
  (`.m-marquee__countdown > .m-countdown { --countdown-direction: row; }` —
  it must be the root, because a knob declared there beats the same property
  inherited from an ancestor). The inner module's internals are off limits;
  needing them means it is missing a knob. See the nesting section in
  `CLAUDE.md`.
- **Declare the pre-enhancement state** if the first paint differs visibly
  from the enhanced one. `@use "progressiveEnhancement" as *;` and wrap the
  rules in `pre-enhancement("data-<name>-ready")`. The mixin assumes the flag
  and the rule share a subject; where they cannot (`tabs` has no root class to
  nest its panel rules under), write the same two conditions out with a
  `:not([data-<name>-ready] *)` guard and say why. The block only ever ships
  when it is **survivable** — nothing
  lost, a `:target` escape hatch, or a bail-out that lifts the state — because
  a chunk that never arrives makes it permanent. Where it is not, document the
  rule in the snippet as an opt-in instead of shipping it. Full decision table
  and the reasoning in [`preEnhancement.md`](preEnhancement.md).
- **Focus ring is opt-in per element** via the `focus-ring()` mixin
  (`@use "focus" as *;`). Pick the tone by the element's own surface (the theme
  is dark → almost always `light`). See the focus-ring section in `CLAUDE.md`.
- **Hiding a label visually** goes through the `visually-hidden` mixin
  (`@use "visuallyHidden" as *;`) — never a local copy of the recipe. It is
  for text that must keep naming a control whose glyph is `aria-hidden`
  (`siteSearch`, `backToTop --iconOnly`, `offCanvasNav`'s icon-only burger),
  not a way to hide something: that is `display`/`visibility`, which take the
  element out of the accessibility tree too.
- Animation/transition is a **pure CSS progressive enhancement**
  (`@starting-style`, `allow-discrete`); older engines just snap. Always add a
  `@media (prefers-reduced-motion: reduce)` block that makes it instant.
- Use **logical properties** (`inset-inline-end`, `inline-size`) as the house
  style: they read better next to `inset-block` / `block-size` and keep one
  rule where physical sides would need two. **Not** as RTL preparation —
  right-to-left is explicitly out of scope for this project (see `CLAUDE.md`),
  so never add direction detection in JS to go with them.
- **Media takes its box from its container.** An `<img>`/`<video>` gets
  `display: block; inline-size: 100%; block-size: 100%; object-fit: cover` and
  no dimensions of its own — the size and the `aspect-ratio` come from the
  container the consuming project styles, which is also what reserves the
  layout space before the image arrives. Say so in the snippet (§7): those
  container styles are part of the wiring. `video` is the reference file; the
  named exceptions (`contain` for a surface that must show the whole frame,
  iframes, SVG) are in the media-sizing section of `CLAUDE.md`.
- **Behaviour-only components ship a stub stylesheet** and leave visuals
  (including focus) to the consuming project (`formValidation`,
  `inputCharCount`, `inlineSVG`, `scaleSVG`). A component may also ship *only*
  the rules it cannot work without and still leave every visual to the
  project: `marquee`'s clipping flex row, `tabs`' pre-enhancement block. Both
  are structure, not design — the project could not write either one later,
  and in the `tabs` case getting it wrong makes content unreachable rather
  than ugly.


## 7. `<name>.html` (copy-paste snippet)

A leading comment banner titled `<name> — copy-paste snippet`, with:
1. the three `/dist` includes (`shared.min.css`, `<name>.min.css`,
   `boot.min.js`) and the note that boot lazy-loads the module — the author
   never imports `<name>.js`;
2. how to place the markup and wire it (`data-js-behavior`, the behavioural
   `data-*` attributes) — including, where the component renders media, the
   container styles the project has to supply (see §6 and `CLAUDE.md`);
3. a **Notes / Configuration** section covering progressive-enhancement
   behaviour and every optional attribute with its default. Where the
   component ships a pre-enhancement state, say what it hides and what
   happens if the chunk never arrives; where it deliberately does not, give
   the opt-in rule and name the trade.

Then the actual, minimal ready-to-paste markup.


## 8. `readme.md`

Sections, in this order:
- `# <name>` + one-line summary.
- `## Files needed to copy` — the three files, plus any bundled
  `_shared/js/*.js` utility to copy when pasting into a plain project.
- `## Usage` — how to wire it and what each option does.
- `## Accessibility` — when there is anything to say.
- `## Integration` — that JS exports `init(el, services)`, is boot-loaded per
  `data-js-behavior`, sets no inline styles, and that `services.reporter` is
  optional (used only for warnings).
- `## Demo` — "Open `demo.html` in the browser (requires a prior `gulp build`)."


## 9. `demo.html`

Standalone page loading the **built** assets from `../../../dist/` plus the
`dev_*` helper scripts from `src/_shared/js/`. Structure:
`<main class="shell"> → <section class="hero"> (back link + h1 + blurb) →
<section class="stage" aria-label="Live demo">`. Inside the stage, a comment
block explaining wiring / progressive enhancement / accessibility, `stage__intro`
paragraphs, and several live examples exercising each mode of the component.


## 10. Shared building blocks (reference)

- **JS utilities** (`_shared/js/`, all direct imports): `rafThrottle`,
  `debounce`, `getCssCustomProperty`, `resolveLocale`, `formatTemplate`
  (interpolate `{placeholder}` tokens in a localized template),
  `decodeFragment` (a URL fragment to the id it addresses),
  `parseNonNegative` (a px option, with a fallback), `uniqueId` (an id that is
  free in the document), `focusableSelector` (elements the keyboard already
  reaches), `describedBy` (add/remove one id in a field's `aria-describedby`),
  `navExpandedMediaQuery` (the `--bp-navigation` query), `otherModalOpen` (is
  another modal `<dialog>` still up). Plus `createReporter` (via DI in
  `boot.js`).
- **Dev-only** helpers loaded by demos: `dev_pageInfo`, `dev_a11yInspector`,
  `dev_qrCode`.
- **SCSS tokens** (`_shared/scss/`): `_foundations` (space/animation/radius),
  `_colors_primitives` + `_colors_semantic`, `_focus` (mixin only),
  `_visuallyHidden` (mixin only — `visually-hidden`, for the text node that
  names an icon-only control), `_progressiveEnhancement` (mixin only —
  `pre-enhancement`, the state that covers the gap before `init()`),
  `_breakpoints` / `_mediaqueries`, `_functions`.
- **Shared media** (`_shared/media/img/`): `icons/`, `system/`. Note: the build
  does **not** copy `media` into `dist`, so reference icons inline
  (`currentColor`) or via a project-served path, not a `dist`-relative one.
